### Изменение — один глагол разделён на два: «снять статус архивации» и «очистить архивные файлы»

**Проблема была не в формулировке, а в семантике.** Раньше у панели была одна операция, а кнопка называлась «Удалить выбранное» —
это не было удалением (не удалено ни одного байта) и не было одной-единственной вещью (менялся массив, а объявлялось «удаление»).
В итоге одно и то же действие звалось тремя именами (удалить / очистить / убрать), и ни игроки, ни имплементаторы не могли сойтись.

Теперь оно разделено на две операции с **отдельным маршрутом, отдельной кнопкой, отдельным подтверждением**:

| | Снять статус архивации | Очистить архивные файлы |
|---|---|---|
| Маршрут | `session-history-prune` | **`session-history-purge`** (новый) |
| Что меняется | только `global.archivedSessionIds` | удаление сущностей с диска **+** правка двух списков id |
| Файлы на диске | нетронуты | **исчезают** |
| Судьба сессии | возвращается в исходное рабочее пространство боковой панели | исчезает из мира |
| Обратимо | ✅ вступает в силу после перезапуска | ❌ **необратимо** |

«Очистить архивные файлы» одним махом трогает 4 места:

1. `~/.dsh/sessions/<рабочее пространство>/<id сессии>/` — **весь каталог**. Фактически в 3 каталогах одновременно лежали
   `session.jsonl.zstd` и старый формат `session.v3.jsonl.zstd`; удалить только копию текущего формата — оставить мусор.
2. `~/.dsh/storages/session_projcache/sessions/<id сессии>.json` — кэш проекций, запись за записью.
   > Внимание: есть ещё один `storages/session_projcache.json` (вся раскладка целиком, 99,4 МБ, последняя запись застыла на
   > 09-11): это **окаменелость**, оставленная миграцией раскладки; хост давно его не пишет, и этот плагин его тоже не трогает.
   > Живой кэш проекций — `session_projcache/sessions/` (замер: 143,4 МБ / 275 записей, пишется и сегодня).
3. `workspace.json` → `global.archivedSessionIds`
4. `workspace.json` → `tables.workspaces.*.sessionIds`

**Очистка с необходимостью тянет за собой снятие статуса архивации**: если файлы удалены, а id остались в массиве — это архивы-зомби —
боковая панель их не видит, а как только снять архивацию, вылезет пустая сессия, которую не открыть.

**Порядок исполнения: «сначала правим файлы, потом удаляем сущности»**: правка файлов атомарна и может быть прервана целиком
(если файл хранилища недоступен — **не удаляется ни один байт**); наоборот — сначала удалить сущности, потом править файлы — сбой на полпути оставит id-зомби.

**Ограждения разрушительной операции**:

- без `dshHome` исполнение сразу отказывается — никаких угаданных путей;
- перед удалением `isSafeChild` утверждает, что цель — потомок **ожидаемого точного уровня** под ожидаемым корнем
  (ошибся уровнем — и снесён весь корень `sessions`);
- каждая запись независима; сбои только фиксируются, не бросаются, с деталями `failures`, панель перечисляет их построчно;
- сохранён единственный вход записи `editWorkspaceDocument` (резервная копия + временная запись в том же каталоге + атомарное переименование).

### Изменение — размер считается по «отмеченной единице», без общего итога

Занимаемый одной сессией объём колеблется крайне сильно (замер: одна projection-cache 23,47 МБ при транскрипте 0,07 МБ;
бывают и нулевые байты). Поэтому:

- **каждая строка** показывает своё `транскрипт 6,2 МБ · кэш 2,3 МБ`;
- заголовок списка показывает `всего 72 записи · 98,6 МБ`;
- кнопка показывает **подытог выбранных**: `Очистить архивные файлы (3) · освободит 38,2 МБ`;
- окно подтверждения перечисляет размеры по записям + сумму.

### Исправление — «без реакции» очистки в «Доме престарелых»: читавший и писавший не работали с одними данными

**Симптом**: в режиме правки отметить архивные сессии → `confirm` → сообщение об успешной очистке, но список **не уменьшился ни на одну запись**,
и на панели нет никакого видимого изменения — выглядит как полное отсутствие эффекта.

**Корень**: два маршрута признавали каждый свой набор данных, **никак не связанные между собой**.

| Маршрут | признаваемый набор |
|---|---|
| `session-history-prune` | `global.archivedSessionIds` файла хранилища `~/.dsh/storages/workspace.json` (резервная копия + атомарная замена) |
| `session-history-list` | **приоритет у памяти хоста `workspaceRegistry.archivedSessionIds`** (откат к файлу только если он нечитаем) |

`registry` — снимок, загруженный хостом **при запуске**; прямая правка файла в него не записывается. Итог:

- файл реально худел (замер: 166 → 159 → 151 → 103 → 72 → 71, каждое подтверждение оставляло резервную копию `.bak-*`);
- но список всегда возвращал те же записи — пользователь отмечал в том же порядке и каждый раз удалял «первые записи списка»,
  а сам список вовсе не менялся; отсюда ощущение «нажал подтвердить, ничего не произошло».

**Лечение**: сделать список и prune **одного источника**.

- `readArchiveSet` переходит на **приоритет файла хранилища**, `registry` отступает в роль отката при отсутствующем файле;
  registry по-прежнему читается, но возвращается лишь как диагностическая поверхность (`registryIds`).
- `session-history-list` добавляет `pendingRestart`: число id, которые **есть** в registry, но **нет** в файле
  — то есть висящие позиции «уже очищены с диска, но в этом процессе ещё действуют». Панель в ответ показывает жёлтое предупреждение
  и общее число строк списка, чтобы «одной записью меньше» было проверяемо на глаз.
- `pruneHistory` получает **проверку после записи**: после обратной записи файл перечитывается, чтобы подтвердить, что целевые id действительно исчезли,
  иначе честно сообщается об ошибке; больше никаких «панель говорит успех, файл на деле не изменился».

### Известный риск — хост записывает обратно весь снимок памяти; очистку можно «воскресить»

Слой хранилища (`dsh-storage-json`) работает как **полная перезапись, память — приоритет**: каждая запись сериализует состояние памяти
как целый документ поверх файла, и отдельного flush при выключении нет. Поэтому после очистки и до перезапуска
**любое изменение архивов или рабочих пространств записывает обратно целиком старые `archivedSessionIds`**, сводя очистку к нулю.

Это не баг этого плагина (у официальной стороны нет конечной точки unarchive; файл — единственная доступная для записи поверхность),
но пользователь должен об этом знать — это уже прописано в окне подтверждения и в сообщении об успехе: **после очистки немедленно перезапустите DSH**.

  Этот плагин раньше рендерил только голую строку, поэтому было два несоответствия:
  1. в разделе он не совпадал с формой «раскладного ящика» остальных плагинов;
  2. `card.title` (Session Steward) и `card.desc` (файлы истории · проверка здоровья) были **определены, но никогда не рендерились**,
     мёртвый текст — это и был «пропущенный пункт ящика».

  Теперь шапка восстановлена (заголовок + описание + шеврон, весь блок кликабелен для переключения), тело по умолчанию свёрнуто,
  как у прочих карточек раздела; `aria-expanded` синхронно отражает состояние развёрнутости.
- **Поведение при недоступности сервиса настроек**: раньше вся карточка деградировала в строку «сервис настроек недоступен»
  и вместе с тем **теряла даже заголовок**; теперь шапка ящика рендерится как обычно, а причина объясняется только в теле —
  этот плагин больше не исчезает из раздела полностью.

### Изменения

- Переключение развёрнутого состояния и поворот шеврона уважают `prefers-reduced-motion`.

## 0.1.0-alpha.3

Кэш результатов осмотра: повторное открытие панели выдаёт содержимое без задержки, а после вмешательства обновляется только та строка.

### Новое

- **Кэш результатов осмотра (внутри процесса)**: после полного сканирования (порциями по всему корпусу) результаты остаются в процессе хоста;
  при повторном открытии панели кэш рендерится сразу, без полного пересканирования. Кэш **складывается только после полного прохода корпуса** —
  закрытие панели на полдороге не оставит половину результата, выдающую себя за полный вывод.
- **`resume` как щуп чистого чтения**: `session-health-scan` принимает `resume: true`, **только читает кэш, ничего не сканирует**.
  При монтировании панели это бесплатное однократное прощупывание: есть попадание — показываем содержимое, нет — не делаем ничего
  (гробить тяжёлой работой монтирование было претензией к прошлой версии). Одновременно возвращается текущий общий размер корпуса.
- **Время генерации и вход обновления**: при попадании в кэш панель показывает «результаты из кэша · N минут назад» и даёт «Обновить»
  (принудительное полное пересканирование). Старые результаты никогда не выдаются за свежий скан.
- **Уведомление об изменении корпуса**: если закэшированный общий размер корпуса не совпадает с текущим, показывается «корпус изменился (a → b), рекомендуется обновить».
  Эта сверка делает лишь перечисление каталогов, очень дёшево — потому и не составляет новой политики инвалидации кэша.

### Изменения

- **Перезапись строки на месте**: после осмотра отдельной сессии и обратимого вмешательства пересканирование больше не нужно —
  вмешательство и так пересчитывает отчёт `after`, он пишется прямо в кэш; когда панель возвращается к списку, строка уже свежая
  (вылеченная строка отныне исчезает из списка, в согласии с «перечислять только проблемы»).
- Кэш **не пишется на диск**: обнуляется при перезапуске DSH. Персистентность потребовала бы политики инвалидации, а цена суждения об устаревании
  (перечислить корпус, сверить mtime/size журналов) почти равна пересканированию; этот срез берёт YAGNI.

### Тесты

- Добавлен `tests/cache.spec.ts` (19 случаев): правила сложения (неполный проход / полный / пустой корпус / прерван на середине / `clear`),
  все ветви перезаписи отдельной строки (добавление / замена / выписан после излечения / no-op) и разводка `handleMethod`
  (`resume` не сканирует, попадание после полного порционного прохода, `onlyProblems=false` не засоряет кэш,
  идентичность объекта, перезаписанного после вмешательства, рантайм без кэша остаётся работоспособным).

## 0.1.0-alpha.2

Исправление суждения и подачи вмешательства (рецепта): больше не выписывается рецепт воротам, «которые не в силах судить», и после вмешательства даётся явный вывод.

### Исправления

- **Ошибочный рецепт для `skipped` (важно)**: `prescribe()` по `level !== 'ok'` судил, надо ли отправлять кэш проекций в карантин;
  «эти ворота не могут судить» посчиталось «кэш проекций не выровнен», из-за чего против собственных же доказательств выписывался само-противоречивый рецепт
  с предложением поместить в карантин **несуществующую** запись. Выделен общий предикат `isActionable()` (обрабатываемы только `warn` / `fail`), всё сведено в одну точку:
  планка уровней в `gates.ts` и критерий вмешательства в `repair.ts` отныне — одно и то же.
- **Ложные «все четыре ворота зелёные»**: без позиций для вмешательства вперёд возвращался ответ «все четыре ворота зелёные». Когда ворота `skipped` (судить нечем, а не зелёные), эта формула несправедлива;
  теперь: «обрабатываемых позиций нет (N ворот не в силах судить, не аномальны): <список id ворот>».
- **После вмешательства аномалия всё ещё на экране — непонятно, сработало ли**: панель рендерила только две ступени «до / после вмешательства»;
  когда обе аномальны, «вмешательство провалилось» и «вмешательство не имеет отношения к очагу» неразличимы.
  Хост получает `assessRepair({ before, after, repair })`, выносящее вердикт по одной из пяти ступеней с человекочитаемым пояснением:
  `nothing-to-do` (все четыре ворота зелёные) / `repaired` (восстановлено) / `repaired-with-residual` (кэш отправлен в карантин,
  но остаются аномалии, не связанные с этим кэшем, например open step в журнале сессии) / `not-applicable` (у текущей аномалии нет обратимой позиции вмешательства) /
  `failed` (сбой самого вмешательства). Панель рендерит баннер вывода в цвете ступени.

### Пояснения

- **Способность вмешательства не изменилась**: по-прежнему «в карантин только записи кэша проекций, сначала скопировать потом переместить, журналы сессий не трогать»;
  в этот раз исправлены только **суждение** и **подача**. Типичный сценарий — «аномальны только ворота `cold-read` (у сессии есть незакрытый open step)» —
  такие аномалии и раньше не подлежали починке этим плагином; теперь они явно признаются `not-applicable` с объяснением,
  а не молча показываются как «после вмешательства всё ещё аномально».

### Тесты

- Добавлен `tests/repair.spec.ts` (12 случаев): покрывает четыре ступени `isActionable`, то, что `prescribe` больше не выписывает пустых рецептов,
  и ветви пятиступенчатого суждения `assessRepair`.

## 0.1.0-alpha.1

Исправление суждения и обратной связи панели осмотра: убран массовый ложный сигнал «Внимание», добавлены прогресс сканирования и построчные причины.

## 0.1.0-alpha.0

Первая альфа-версия: Session Steward (файлы истории + проверка здоровья).

### Новое

- **Файлы истории сессий (Архив карт)**: из `dsh-session-search-toggle` перенесены чтение и очистка официального набора архивов,
  поведение эквивалентно добере (резервная копия + временная запись в том же каталоге + атомарная замена; очистка разрешена только в явном режиме правки).
  Разница: источник списка стал **истиной официального набора архивов** (приоритет у registry, откат к файлу хранилища), поскольку независимый индекс ушёл вместе с пакетом поискового индекса;
  заголовок и прочие метаданные — по мере возможностей (снимок заголовка `sessionQuery` → заголовок из кэша проекций → пусто).
- **Проверка здоровья (осмотр → рецепт → выписка)**: четыре независимо тестируемых ворот
  (`log-integrity` / `projection-cache` / `lossless-json` / `cold-read`),
  единый вывод `{ id, level, evidence, attribution, detail }`; агрегируются в `SessionHealthReport`.
- **Индекс атрибуции**: статическое сканирование `node_modules/<pkg>/lib/*.js` профиля, чтобы построить «ключ проекции → имя пакета»
  и вернуть провалившиеся ворота конкретному плагину и пути поля; если не найдено, честно помечается `unknown`.
- **Обратимый рецепт**: карантин повреждённых записей кэша проекций (сначала копия-резерв, затем перенос в `.quarantine-<ts>`) + список команд.
  **Запрещено** переписывать журналы сессий, менять исторические данные, молча отбрасывать поля.
- **Два feature gate**: `historyFiles` / `healthCheck`; в выключенном состоянии соответствующая поддоменная область вообще не регистрируется (явная ошибка disabled),
  и клиент не рендерит соответствующую вкладку.
- **Маршруты**: `/session-steward/api/*`, имена методов всегда `session-*`, полностью изолированы от `index-*` у `/switch-search/api` поискового индекса.

### Известные ограничения

- Воротам `lossless-json` нужна экспозиция `sessionProjections` (горячее состояние) со стороны хоста, чтобы вынести определённый вердикт;
  если её нет, честно деградируют до `warn`, не гадая.
- Скан здоровья по умолчанию перечисляет только последние 30 нездоровых сессий (потолок `limit` — 200), полный обход базы по умолчанию не делается.
- Панель клиента — минимальная реализация (список + подробности + кнопка из трёх шагов), без виртуального скролла и массовых операций.
